# 写作与修订

先读 [内容原则](policy.md)。本指南说明执行步骤；字段约束由 [内容 schema](../../src/content.config.ts) 验证，领域词以 [领域登记表](../../src/lib/domains.ts) 为准。

## 新增文章

1. 确认问题、读者需要、已读取的材料范围和文章的解释边界。来源解读保留原文的主要论证与层次。
2. 从 [中文模板](../templates/article.md) 和 [英文模板](../templates/article.en.md) 复制起稿，在内容集合之外完成材料核验和正文。模板中的占位内容必须替换。
3. 准备发布的文章放在 `src/content/notes/YYYY/MM/slug.md`；年月表示文章归档月份，slug 使用简短的小写英文和连字符。
4. 按格式说明补齐元信息和所需配图。正文从二级标题开始，主题结构按问题本身组织。
5. 两语定稿且发布已获授权后，按 [讨论指南](../operations/discussions.md) 创建或复用共用讨论，登记真实编号。草稿留在集合外，不为预览建帖。
6. 运行 `npm run check`，预览正文、目录、图表、封面及双语评论区；发布前运行 `npm run discussion:check`，再按 [贡献流程](../../CONTRIBUTING.md) 交付。

路径生成文章 URL，例如 `src/content/notes/2026/10/example.md` 对应 `/2026/10/example/`。发布后即使改题目，也保留原路径与归档年月。

所有集合内的 Markdown 都会发布，没有草稿或定时发布过滤。模板、素材摘录和未完成稿留在集合之外；公开仓库中已提交的文件均可被访问。

## 元信息

按 [文章格式与元信息](format.md) 填写，仅使用标准 OKF 字段。修改时间使用 `generated`；创建时间从 Git 历史读取，归档年月和语言从路径派生。来源统一登记在 `sources`，正文用对应 ID 的脚注归属具体论断。

标题、摘要、领域、主要来源与封面由页面模板统一展示。来源作者与本站整理者分别归属。新增领域时同时修改 `domainNames` 和对应的英文名、稳定英文 slug、两语范围说明；不要在文档中再维护一份领域词清单。已发布的领域 key 和 slug 保持稳定。

## 中英文对应

中文文件保留 `src/content/notes/YYYY/MM/slug.md`，英文文件放在 `src/content/notes/en/YYYY/MM/slug.md`。它们分别生成原中文 URL 和 `/en/` 前缀的英文 URL。配对身份与语言均从路径派生，不另加 frontmatter 字段。

两版必须一起完成后再发布；只有一版会使自动检查失败。英文需要完整翻译正文、定义、表格、案例、图表节点和参考资料用途，不用摘要代替。中文术语保持“中文(English)”定义，英文只使用对应英文术语，不附中文括注。

- 来源 ID/URL、首项主要来源和共享领域词 key 两版一致；实际编辑时刻独立记录，归档年月与 slug 一致。
- 标题、摘要、来源显示文本、图片 alt 和 credit 需要对应语言；原始来源标题、作者名可保留原文。
- 两版引用同一封面文件；英文相对路径通常回到中文资源目录，按实际目录计算，不复制图片。
- 英文 Mermaid 使用 ```` ```mermaid en ```` 围栏，节点与边标签翻译成英文；`en` 控制图注与辅助提示。中文版使用普通 `mermaid`。
- 两版保持相同主要章节层次、表格和图表数量；自动检查能发现结构缺失，但不能证明翻译意义一致，需要人工核对证据、假设、因果与适用边界。

修订一版的实质内容时同步修订另一版。发布前分别预览两语，检查文/A切换是否到对应页面。

## 修订现有文章

- 勘误、标点或排版微调：保留路径与归档年月，用 Git 提交说明变化。
- 实质内容修订：保留路径与归档年月，更新 `generated.by` 与 `generated.at`，在 Git 提交中说明结论、依据或解释范围的变化。同一天修订也记录真实时刻，页面显示当地时分与时区。
- 仅更换封面：同时更新 Markdown 图片的 alt 与来源说明，图像改变了文章表达时更新 `generated`。不要为了显示新日期而移动文章目录。
- 新增独立论题：建立新文章，并从相关正文关联；不把已有文章改成另一主题。

修改已有文档时，保留完整解释、原文与延伸的区分。来源不足影响主要论证时，先补足输入；实际读取范围和不确定性处理见内容原则。

## 封面与正文图表

封面按当前文章的核心问题构思，一张图集中表达一个主要关系或场景。先确定它要传达什么，再选择构图。它不承担事实证明，也无需容纳全部概念。

- 风格：细线条、少量浅蓝与浅绿淡彩、大量留白的简笔画；简约、不夸张，避免写实材质与冗杂元素；以插画主体与关系表达价值，优先不含文字。
- 构图：优先横向 16:9，主体在缩略图中仍可辨认；兼顾列表小图与正文大图。
- 来源：自行创作、已获许可或可按相应条款使用的图像均可，准确填写来源。生成图像注明 AI 生成，并人工检查内容含义。
- 工具：使用当前可用且获授权的图像工具；工具不可用时交付明确构图说明和缺少的素材，不用无关图片替代。

生成图可在文章旁保存 `.cover.json`，记录工具、构图与实际提示词，便于后续维护；JSON 不属于文章集合。

封面保存在文章旁边，用正文首项标准 Markdown 图片表达，见 [格式说明](format.md#封面归档与原稿)。

站点的 `src/assets/meadow.png` 只用于页首与页尾的淡蓝天、草坪点缀。封面不使用统一风景图。

正文图表用于解释组成、关系、过程或数据。使用必要的 `mermaid` 围栏代码；[beautiful-mermaid](https://github.com/lukilabs/beautiful-mermaid) 决定支持范围，当前文章可作为流程图示例。图表在构建时生成 SVG，继承站点配色；宽图在自身区域横向滚动。语法错误需要修正，不能静默删除图表。二级标题自动进入文章目录，无需手写目录。

## 内容检查

确认定义按层次推进，事实、来源观点、本文推断和假设案例分别说明。引用有对应出处，数据保留时间和口径。预览标题、目录跳转、表格、图表、封面及来源说明；实质更新核对 `generated` 与 Git 说明。

自动检查的范围见 [开发指南](../development/guide.md#检查与通过条件)，发布步骤见 [发布指南](../operations/deployment.md)。
