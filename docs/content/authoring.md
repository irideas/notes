# 写作与修订

先读 [内容原则](policy.md)。本指南说明执行步骤；字段约束由 [内容 schema](../../src/content.config.ts) 验证，领域词以 [领域登记表](../../src/lib/domains.ts) 为准。

## 新增文章

1. 确认问题、读者需要、已读取的材料范围和文章的解释边界。来源解读保留原文的主要论证与层次。
2. 从 [中文模板](../templates/article.md) 和 [英文模板](../templates/article.en.md) 复制起稿，在内容集合之外完成材料核验和正文。模板中的占位内容必须替换。
3. 准备发布的文章放在 `src/content/notes/YYYY/MM/slug.md`；年月与本站首次发布日期一致，slug 使用简短的小写英文和连字符。
4. 按下表补齐元信息和所需配图。正文从二级标题开始，主题结构按问题本身组织。
5. 两语定稿且发布已获授权后，按 [讨论指南](../operations/discussions.md) 创建或复用共用讨论，登记真实编号。草稿留在集合外，不为预览建帖。
6. 运行 `npm run check`，预览正文、目录、图表、封面及双语评论区；发布前运行 `npm run discussion:check`，再按 [贡献流程](../../CONTRIBUTING.md) 交付。

路径生成文章 URL，例如 `src/content/notes/2026/10/example.md` 对应 `/2026/10/example/`。发布后即使改题目，也保留原路径与首次发布日期。

所有集合内的 Markdown 都会发布。没有 `draft` 字段或定时发布机制；未来的 `date` 不会延迟上线。模板、素材摘录和未完成稿留在集合之外；公开仓库中已提交的文件均可被访问。

## 元信息

日期统一使用加引号的 `YYYY-MM-DD` 字符串。必需项为 `title`、`date`、`description`；`tags` 可以省略或为空。

| 字段 | 填写方式 |
|---|---|
| `title` | 当前标题，不在正文重复一级标题 |
| `date` | 本站首次发布日期，决定年月归档 |
| `description` | 清楚概括问题和解释范围，用于列表、SEO 与 RSS |
| `tags` | 至多两个已登记的领域词，不用来源、读者或文章形式作标签 |
| `updated`、`revision` | 实质修订的日期与说明，成对填写 |
| `source` | 有主要来源时填写整组信息；其日期为原始材料发布日期 |
| `asOf` | 现状或趋势分析的资料实际截止日期，按需要使用 |
| `cover`、`coverAlt`、`coverCredit` | 有封面时填写本地图片路径、准确替代文本及来源说明 |

主要来源示例，所有示例值都要替换为真实信息；未知日期可省略：

```yaml
source:
  title: 原始材料标题
  author: 原作者
  publication: 课程、刊物或频道名称
  url: https://example.org/original
```

主要来源由页面模板统一展示。其他证据在正文就近引用，必要时列入参考资料。来源作者与本站整理者分别归属。

新增领域时同时修改 `domainNames` 和对应的英文名、稳定英文 slug、两语范围说明；不要在文档中再维护一份领域词清单。领域中文 key 和英文 slug 形成公开 URL，发布后保持稳定。

## 中英文对应

中文文件保留 `src/content/notes/YYYY/MM/slug.md`，英文文件放在 `src/content/notes/en/YYYY/MM/slug.md`。它们分别生成原中文 URL 和 `/en/` 前缀的英文 URL。配对由路径派生，无需填写 `lang` 或 `translationKey` 字段。

两版必须一起完成后再发布；只有一版会使自动检查失败。英文需要完整翻译正文、定义、表格、案例、图表节点和参考资料用途，不用摘要代替。中文术语保持“中文(English)”定义，英文只使用对应英文术语，不附中文括注。

- 日期 `date`、`updated`、`asOf`，主要来源 `url` 与 `date` 以及共享领域词 key 两版一致。
- 标题、摘要、来源显示文本、修订说明、图片 alt 和 credit 需要对应语言；原始来源标题、作者名可保留原文。
- 两版引用同一封面文件；英文相对路径通常回到中文资源目录，按实际目录计算，不复制图片。
- 英文 Mermaid 使用 ```` ```mermaid en ```` 围栏，节点与边标签翻译成英文；`en` 控制图注与辅助提示。中文版使用普通 `mermaid`。
- 两版保持相同主要章节层次、表格和图表数量；自动检查能发现结构缺失，但不能证明翻译意义一致，需要人工核对证据、假设、因果与适用边界。

修订一版的实质内容时同步修订另一版。发布前分别预览两语，检查文/A切换是否到对应页面。

## 修订现有文章

- 勘误、标点或排版微调：保留 `date` 和路径，用 Git 提交说明变化。
- 实质内容修订：保留 `date` 和路径，更新 `updated` 与 `revision`，说明结论、依据或解释范围的变化。同一天修订也填写这两个字段，页面会合并同日日期展示。
- 仅更换封面：同时更新 `coverAlt`、`coverCredit`；图像改变了文章表达时更新修订说明。不要为了显示新日期而移动文章目录。
- 新增独立论题：建立新文章，并从相关正文关联；不把已有文章改成另一主题。

修改已有文档时，保留完整解释、原文与延伸的区分。来源不足影响主要论证时，先补足输入；实际读取范围和不确定性处理见内容原则。

## 封面与正文图表

封面按当前文章的核心问题构思，一张图集中表达一个主要关系或场景。先确定它要传达什么，再选择构图。它不承担事实证明，也无需容纳全部概念。

- 风格：细线条、少量浅蓝与浅绿淡彩、大量留白的简笔画；简约、不夸张，避免写实材质与冗杂元素；以插画主体与关系表达价值，优先不含文字。
- 构图：优先横向 16:9，主体在缩略图中仍可辨认；兼顾列表小图与正文大图。
- 来源：自行创作、已获许可或可按相应条款使用的图像均可，准确填写来源。生成图像注明 AI 生成，并人工检查内容含义。
- 工具：使用当前可用且获授权的图像工具；工具不可用时交付明确构图说明和缺少的素材，不用无关图片替代。

生成图可在文章旁保存 `.cover.json`，记录工具、构图与实际提示词，便于后续维护；JSON 不属于文章集合。

封面保存在文章旁边，示例：

```yaml
cover: ./example.png
coverAlt: 准确描述实际画面中的主体与关系。
coverCredit: 图片来源或生成说明
```

站点的 `src/assets/meadow.png` 只用于页首与页尾的淡蓝天、草坪点缀。封面不使用统一风景图。

正文图表用于解释组成、关系、过程或数据。使用必要的 `mermaid` 围栏代码；[beautiful-mermaid](https://github.com/lukilabs/beautiful-mermaid) 决定支持范围，当前文章可作为流程图示例。图表在构建时生成 SVG，继承站点配色；宽图在自身区域横向滚动。语法错误需要修正，不能静默删除图表。二级标题自动进入文章目录，无需手写目录。

## 内容检查

确认定义按层次推进，事实、来源观点、本文推断和假设案例分别说明。引用有对应出处，数据保留时间和口径。预览标题、目录跳转、表格、图表、封面及来源说明；实质更新核对修订字段。

自动检查的范围见 [开发指南](../development/guide.md#检查与通过条件)，发布步骤见 [发布指南](../operations/deployment.md)。
